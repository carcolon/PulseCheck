PulseCheck API · Documentacion tecnica

Este repositorio concentra el backend operativo de PulseCheck. Expone autenticacion administrativa con Entra ID, administracion de usuarios admin, administracion de campañas, sincronizacion del agente, persistencia en Azure SQL, SignalR para eventos en tiempo real y exportes. La arquitectura actual sigue un esquema de capas separadas entre dominio, aplicacion, infraestructura y API.

1. Objetivo y alcance

Responsabilidad

API HTTP y hubs SignalR para el panel administrativo y para los agentes Windows.

Persistencia

Modelo relacional sobre Azure SQL con tablas para campañas, respuestas, dispositivos, sesiones y eventos de actividad.

Integracion

Recibe llamadas del panel React y del agente desktop. Emite eventos en tiempo real al panel administrativo.

Bootstrap

  • Program.cs carga configuracion PulseCheck y registra infraestructura.
  • PulseCheckService centraliza la logica operacional usada por controllers.
  • Se publican dos hubs: /hubs/notifications y /hubs/admin-notifications.
  • La autenticacion administrativa usa AdminBearer y sesiones persistidas en base de datos.
  • Las rutas administrativas y hubs usan politicas de rate limiting registradas en Program.cs.
  • Se inicializa la base de datos al arranque con PulseCheckDbInitializer.

4. Endpoints y contratos principales

Area Endpoint o hub Funcion
Autenticacion POST /api/auth/login, POST /api/auth/entra, GET /api/auth/session, POST /api/auth/logout Gestiona sesiones administrativas y acceso federado con Entra ID. En produccion el login local queda deshabilitado con AllowLocalAdminLogin=false.
Administradores GET /api/admin-users, POST /api/admin-users, DELETE /api/admin-users/{id} Lista, crea y elimina admins autorizados. La creacion usa email normalizado, AuthenticationMode=Entra, IsActive=true y sin password local.
Campañas /api/campaigns Alta, consulta, edicion y operacion de campañas.
Agente POST /api/agent/register, POST /api/agent/sync, POST /api/agent/activity-events Registro del dispositivo, sincronizacion de campañas y envio de eventos de bloqueo, desbloqueo y suspension.
Dashboard GET /api/dashboard/overview, GET /api/dashboard/summary, GET /api/dashboard/report/excel Entrega KPIs, tendencias, alertas y exportes del panel administrativo. El Excel de respuestas incluye escala y respuesta para preguntas numericas.
Tiempo real /hubs/notifications, /hubs/admin-notifications Notificaciones de cambios operativos para agentes y para administradores.

5. Modelo de datos vigente

Tabla Uso Campos relevantes
Campaigns Configuracion de campañas y preguntas Nombre, audiencia, estado, regla de programacion, ventana de entrega, JSON de preguntas, creador, timestamps.
Devices Inventario operativo de agentes DeviceId unico, hostname, usuario, correo, departamento, sistema operativo, version del agente, primera y ultima vista.
Responses Respuestas capturadas Campaña, pregunta, tipo, valor numerico, texto, usuario, dispositivo, hora de respuesta, SubmissionId.
DeliveryLogs Trazabilidad de entrega Estado, error, reintentos, campaign/device binding, timestamps.
AgentActivityEvents Telemetria de bloqueo, desbloqueo y suspension Tipo de evento, razon estimada del lock, segundos de inactividad al bloquear, duracion del evento, usuario, correo, dispositivo.
AdminUsers y AdminSessions Control de acceso administrativo Correo, display name, object id Entra, tenant id, modo de autenticacion, token hash, expiracion, revocacion, user agent e IP.

6. Autenticacion y autorizacion

Panel administrativo

  • Sesion local persistida en AdminSessions.
  • Modo federado con Entra ID soportado por POST /api/auth/entra.
  • La autorizacion final sigue resolviendose contra la tabla AdminUsers.
  • Los admins Entra se gestionan desde AdminUsersController.

Agente desktop

  • No usa login interactivo.
  • Se identifica por metadatos de dispositivo y usuario en register y sync.
  • Actualmente no existe un secreto por agente ni mTLS entre agente y API.
La separacion entre autenticacion administrativa y autenticacion del agente es importante. El panel opera con bearer de sesion administrativa; el agente opera como software corporativo identificado por metadatos del endpoint.

8. Operacion y observabilidad

Tiempo real

SignalR publica respuestas nuevas, actividad de agente y cambios operativos para refrescar el panel sin depender unicamente de polling.

Inicializacion

La base de datos se inicializa al arranque. Esto simplifica ambientes nuevos, pero requiere cuidado en produccion para no mezclar seed con migraciones controladas.

Exportes

La API genera reportes Excel desde el dashboard. Los exportes consumen el estado vigente del repositorio y la base de datos, incluyendo escala y respuesta para preguntas numericas.

9. Riesgos y limites vigentes

  • La identidad del agente todavia se basa en metadatos del endpoint y no en una credencial unica por instalacion.
  • La base SQL se aprovisiona con publicNetworkAccess = Enabled; el control real depende de firewall, cadena de conexion y contexto Azure.
  • No existe API Gateway ni WAF dedicado delante del App Service en el estado actual.
  • El seeding automatico en arranque es comodo para ambientes controlados, pero no reemplaza un proceso formal de migraciones versionadas.
