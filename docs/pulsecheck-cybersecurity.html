PulseCheck - Controles de seguridad implementados

Este documento describe unicamente los controles que PulseCheck tiene implementados en codigo, configuracion, infraestructura declarada o pipeline. El mapeo toma como referencia el documento Information Security Baseline Requirements for New Deployments y agrupa la evidencia por familias de control aplicables a la solucion.

1. Alcance evaluado

Componentes

Panel React, API ASP.NET Core, agente Windows, Azure SQL, SignalR, Azure Static Web Apps, App Service, Application Insights, pipelines y feed de actualizacion.

Baseline

Se consideraron las familias de GRC, IAM, criptografia, logging, vulnerabilidades, Secure SDLC, cloud deployment, endpoints y requisitos especificos de API.

Criterio

Solo se documenta como control vigente aquello que puede observarse en los repositorios, scripts, reportes locales, Bicep, pipelines o comportamiento de la aplicacion.

2. Arquitectura de seguridad vigente

Cliente admin

Browser corporativo que entra al panel React y obtiene acceso por Microsoft Entra ID.

Frontend

Azure Static Web App publica el bundle de PulseCheck Web y consume la API con bearer administrativo.

Backend

Azure App Service aloja ASP.NET Core, controllers, hubs SignalR y validaciones de seguridad.

Datos

Azure SQL persiste campañas, respuestas, dispositivos, sesiones, admins y trazabilidad operativa.

   |
   | Authorization: Bearer <token>

   |
   +-- calcula hash del token
   +-- busca AdminSessions por TokenHash
   +-- valida RevokedAtUtc == null
   +-- valida ExpiresAtUtc > now

13. Controles implementados por familia del baseline

Familia del baseline Estado Control implementado en PulseCheck Evidencia tecnica
IAM, PAM, RBAC/ABAC y autenticacion Implementado El acceso administrativo requiere autenticacion corporativa con Microsoft Entra ID y autorizacion adicional contra AdminUsers en base de datos. Las sesiones administrativas se materializan como tokens aleatorios almacenados solo como hash en AdminSessions. En produccion el login local queda deshabilitado mediante AllowLocalAdminLogin=false. AuthController, EntraAccessTokenValidator, AdminTokenAuthenticationHandler, AdminAuthService, AdminUsersController, appsettings.Production.json.
Ciclo de vida de administradores Implementado El panel incluye una vista de administradores para listar, crear y eliminar usuarios autorizados. La creacion exige solo correo; el registro se guarda como AuthenticationMode=Entra, IsActive=true y sin password local. El primer login Entra completa nombre, object id, tenant y ultimo ingreso. AdminUserService, AdminUsersController, AdminsTab.tsx, useAdminPanel.ts.
Autorizacion de endpoints administrativos Implementado Los endpoints de campañas, dashboard, respuestas recientes, dispositivos, delivery logs administrativos, actividad administrativa y admin-users estan protegidos por [Authorize(AuthenticationSchemes = AdminBearer)]. El hub administrativo de SignalR tambien exige token admin. Controllers de API, AdminNotificationHub, Program.cs.
API-specific requirements Implementado La API aplica autenticacion bearer, CORS restringido por origen configurado, HTTPS redirection, rate limiting por politica para auth/admin-api y validaciones de entrada en operaciones sensibles. Program.cs, CampaignsController, ResponsesController, PlainTextSecurity.
Input validation y proteccion contra contenido no deseado Implementado Las campañas y respuestas abiertas validan texto plano. Se rechaza HTML, entidades decodificadas con signos de markup, esquemas peligrosos como javascript: y handlers como onclick=. Las respuestas numericas se validan contra la escala definida de la pregunta. PlainTextSecurity, PulseCheckService.SubmitResponseAsync, normalizacion de preguntas de campaña.
Criptografia, certificados y transporte Implementado La infraestructura de API exige HTTPS en App Service y TLS minimo 1.2. El backend tambien ejecuta UseHttpsRedirection. La validacion Entra usa metadatos OpenID Connect por HTTPS y valida issuer, audience, firma, lifetime y scope. infra/main.bicep, Program.cs, EntraAccessTokenValidator.
Inventario de activos y dispositivos Implementado La tabla Devices mantiene inventario operativo de agentes con device id, hostname, usuario, correo, departamento, sistema operativo, version del agente y ultima vista. El panel muestra esta informacion en la vista de agentes. Device, AgentController, DevicesController, AgentsTab.tsx.
Logging, monitoreo y trazabilidad Implementado PulseCheck registra delivery logs, respuestas, eventos de actividad del agente, sesiones administrativas, IP/user-agent de sesion y logs locales del agente. La infraestructura incluye Application Insights para telemetria de la API. DeliveryLogs, AgentActivityEvents, AdminSessions, DiagnosticLog, infra/main.bicep.
Vulnerability and patch management Implementado El workspace incluye escaneo local para Semgrep, gitleaks, dependencias .NET vulnerables y npm audit. Tambien conserva reportes de severidad y resultados de ejecuciones previas. scan-local.ps1, semgrep.yml, reports/, latest-*.json.
Secure SDLC Implementado La solucion separa dominio, aplicacion, infraestructura y API; el frontend separa vistas, hooks, tipos y utilidades; los pipelines compilan y publican artefactos por repositorio. Los cambios recientes fueron validados con build antes de push. PulseCheck.slnx, package.json, azure-pipelines-*.yml, estructura de carpetas.
Cloud deployment Implementado La infraestructura principal esta declarada como codigo para Azure: Static Web App, App Service, Azure SQL, Application Insights y configuracion de app settings por entorno. PulseCheck-api/infra/main.bicep, pipelines de API, web y agente.
Endpoint agent controls Implementado El agente usa mutex de instancia unica, cola local para resiliencia, logs locales, estado runtime visible, deteccion de lock/unlock/suspend/resume y auto-update por feed de release. Worker, LocalQueueStore, SessionActivityMonitorService, AutoUpdateService, AgentRuntimeState.
Data handling y exportes Implementado Las respuestas se guardan con tipo de pregunta, pregunta respondida, valor numerico o texto, usuario, equipo y submission id. El dashboard y el Excel muestran la escala asociada a respuestas numericas para preservar contexto de interpretacion. PulseResponse, PulseResponseDto, PulseCheckExcelReportBuilder, ResponsesTab.

14. Controles por superficie

Panel administrativo

  • Login corporativo con Microsoft Entra ID.
  • Autorizacion final en base de datos mediante AdminUsers.
  • Sesion administrativa con token bearer y expiracion server-side.
  • Logout con revocacion de sesion.
  • Vista de administradores para alta y baja controlada.

API y datos

  • Controllers administrativos protegidos con AdminBearer.
  • Rate limiting para autenticacion, API administrativa y hubs.
  • CORS configurado por origen permitido.
  • Validacion de texto plano en campañas y respuestas abiertas.
  • Exportes Excel generados server-side desde datos persistidos.

Agente Windows

  • Identidad operacional por dispositivo, usuario y hostname.
  • Cola local para reintentar respuestas cuando hay fallos transitorios.
  • Reporte de actividad de sesion y eventos de energia.
  • Auto-update con feed de paquetes versionados.
  • Logs diagnosticos locales.

Pipeline y evidencia

  • Repositorios separados para API, web y agente.
  • Build y despliegue por Azure Pipelines.
  • Infraestructura Azure declarada en Bicep.
  • Reportes locales de SAST/SCA/secret scanning.
  • Documentacion tecnica versionada en el workspace.
