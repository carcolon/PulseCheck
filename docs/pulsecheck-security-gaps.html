Brechas y refuerzos

PulseCheck - Carencias frente al baseline y acciones recomendadas

Este documento separa lo que falta o conviene reforzar. La guia principal de ciberseguridad documenta solo controles existentes; aqui se listan brechas, riesgos residuales y mejoras sugeridas alineadas al baseline Information Security Baseline Requirements for New Deployments.

1. Lectura ejecutiva

Refuerzos de codigo recomendados

  • Autenticacion fuerte del agente con credencial por instalacion, certificado cliente o token firmado rotado.
  • Endpoint de administracion con roles granulares para separar permisos de lectura, campañas y gestion de admins.
  • Auditoria explicita para acciones administrativas: crear admin, eliminar admin, crear campaña, activar campaña, exportar Excel.
  • Protecciones adicionales anti-abuse en endpoints publicos del agente: rate limit especifico, validacion de version y allowlist de client capabilities.

Refuerzos de plataforma recomendados

  • Azure Key Vault para cadenas de conexion, secretos Entra y material sensible.
  • Private endpoint o restriccion de red mas fuerte para Azure SQL.
  • WAF/API Gateway delante de App Service.
  • SIEM corporativo con retencion, alertas y correlacion de eventos de App Service, SQL, Entra y agente.
El principal refuerzo de codigo es la identidad del agente. Hoy los endpoints del agente aceptan metadatos del dispositivo y usuario; para alinearse mejor al baseline de API, endpoint y Zero Trust, cada instalacion deberia autenticarse con una credencial no reusable y revocable.

2. Matriz de brechas

Prioridad Area del baseline Carencia actual Riesgo Accion recomendada Tipo
P1 API-specific / IAM / Zero Trust Los endpoints del agente no usan una credencial unica por instalacion, mTLS ni token firmado por dispositivo. Suplantacion de agente o insercion de telemetria/respuestas desde clientes no autorizados si alguien conoce el contrato HTTP. Emitir una credencial por instalacion durante enrolamiento controlado. Validarla en AgentController, ResponsesController, DeliveryLogsController y AgentActivityController. Considerar certificados cliente si TI puede desplegarlos. Codigo + plataforma
P1 Cloud network / Data and databases Azure SQL mantiene public network access en la infraestructura declarada. Mayor superficie de red para la base de datos. Evaluar private endpoint, firewall restringido a App Service/VNet o arquitectura con VNet integration. Infraestructura
P1 Secrets and keys Los secretos se manejan por app settings y variable groups; no hay Key Vault integrado en el flujo declarado. Rotacion y auditoria de secretos menos robusta. Migrar connection strings, client secrets y valores sensibles a Key Vault con referencias desde App Service y pipelines. Infraestructura
P1 API protections No hay WAF/API Gateway dedicado delante del App Service. Menor capacidad de proteccion centralizada ante patrones maliciosos, bots, payloads anormales o abuso de capa 7. Publicar API detras de Azure Front Door WAF, Application Gateway WAF o API Management segun el modelo operativo. Plataforma
P2 RBAC / Least privilege El panel maneja administradores como rol unico. Todos los admins tienen capacidad equivalente sobre campañas, dashboard y gestion de admins. Agregar roles en AdminUsers o tabla relacionada: Reader, CampaignManager, AdminManager, Auditor. Aplicar policies en controllers. Codigo
P2 Logging / SIEM / Audit Hay logs operativos, pero no auditoria formal de acciones administrativas de alto impacto. Dificulta responder quien creo/eliminio admins, activo campañas o exporto datos. Agregar tabla AdminAuditEvents con actor, accion, entidad, diff resumido, IP, user-agent y timestamp. Emitir eventos desde servicios de aplicacion. Codigo
P2 Secure SDLC / OWASP El scanner existe localmente; no hay evidencia en esta documentacion de ejecucion obligatoria como quality gate en todos los pipelines. Riesgo de que cambios inseguros entren si no se ejecuta el scanner antes del despliegue. Agregar etapa obligatoria de SAST/SCA/secret scanning a pipelines API, web y agente; fallar build por severidad alta/critica. Pipeline
P2 Endpoint security El agente es proceso de usuario con tray; no esta separado como Windows Service per-machine. Mayor facilidad para cierre manual, manipulacion local o desinstalacion por el usuario. Migrar a servicio Windows para sync, identidad y envio; dejar companion UI solo para popup/tray. Desplegar con herramienta corporativa de endpoints. Codigo + endpoint management
P2 Data handling / DLP No hay etiquetas formales de clasificacion ni control DLP sobre exportes Excel. Los reportes pueden circular fuera del contexto previsto. Agregar metadata visible de clasificacion en el Excel, watermark o hoja de manejo de datos. Integrar controles DLP corporativos si aplica. Codigo + proceso
P3 BCDR No hay runbook de RTO/RPO, respaldo/restauracion y responsables operativos dentro del paquete documental. Recuperacion no estandarizada ante incidente o perdida de datos. Documentar RTO/RPO, backup de Azure SQL, restauracion probada, owners y comunicacion de incidente. Proceso
P3 Cloud posture / CSPM No hay evidencia local de Defender for Cloud, Azure Policy o guardrails CSPM. La postura cloud depende de revisiones manuales o configuraciones externas no documentadas. Documentar y aplicar Azure Policy, Defender for Cloud, recomendaciones de seguridad y excepciones aprobadas. Plataforma
P3 Frontend performance / SDLC El build web advierte bundle grande. Experiencia movil menos eficiente y mayor superficie de carga inicial. Aplicar code splitting por rutas/tabs y lazy loading de graficas o modulos administrativos menos frecuentes. Codigo

3. Cambios de codigo sugeridos en orden pragmatico

  1. Credencial por agente: agregar tabla de enrolamiento de agentes, token hash por instalacion y validacion obligatoria en endpoints no admin.
  2. Auditoria admin: crear AdminAuditEvents y registrar alta/baja de admins, cambios de campaña, cambios de estado y exportaciones.
  3. RBAC granular: extender AdminUsers con roles o claims persistidos y aplicar authorization policies por controller/action.
  4. Headers y hardening HTTP: agregar middleware de security headers para API y revisar headers de Static Web App.
  5. Export controls: agregar clasificacion y contexto de sensibilidad al Excel, incluyendo fecha, actor que exporta y alcance del reporte.
