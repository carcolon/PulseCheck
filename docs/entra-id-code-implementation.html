Implementacion de Microsoft Entra ID a nivel de codigo

Este documento explica como PulseCheck integra autenticacion corporativa con Microsoft Entra ID desde el frontend React hasta la API .NET. El diseno no usa directamente el token Entra para proteger todos los endpoints: primero valida el access token de Entra y luego emite una sesion interna AdminBearer.

API: ASP.NET Core Frontend: React + MSAL Browser Sesion interna: AdminBearer Scope requerido: access_as_user

Resumen ejecutivo

Que esta implementado

El codigo soporta login con Microsoft Entra ID mediante MSAL en el frontend, validacion JWT en la API, autorizacion adicional contra la tabla AdminUsers y emision de una sesion interna para consumir endpoints administrativos.

Estado de configuracion actual

En los archivos appsettings.json y appsettings.Production.json, PulseCheck:Entra:Enabled esta en false y los IDs estan vacios. La integracion existe en codigo, pero debe habilitarse con configuracion real por ambiente.

Frontend Preparado
Usa @azure/msal-browser y variables VITE_ENTRA_*.
API Preparada
Valida issuer, audience, firma, lifetime y scope.
Ambiente Requiere valores
Tenant, Web Client ID, API Client ID y habilitacion.

Configuracion backend

La API enlaza la seccion PulseCheck al modelo PulseCheckOptions. Dentro de ese modelo vive la configuracion de Entra. 

public sealed class EntraOptions
{
    public bool Enabled { get; init; }
    public string TenantId { get; init; } = string.Empty;
    public string TenantDomain { get; init; } = string.Empty;
    public string ApiClientId { get; init; } = string.Empty;
    public string WebClientId { get; init; } = string.Empty;
}

Registro en Program.cs

En Program.cs la API registra las opciones, el validador de Entra y el esquema propio de autenticacion: 

builder.Services.Configure<PulseCheckOptions>(
    builder.Configuration.GetSection(PulseCheckOptions.SectionName));

builder.Services.AddSingleton<EntraAccessTokenValidator>();

builder.Services
    .AddAuthentication(AdminTokenAuthenticationDefaults.Scheme)
    .AddScheme<AuthenticationSchemeOptions, AdminTokenAuthenticationHandler>(
        AdminTokenAuthenticationDefaults.Scheme,
        _ => { });

builder.Services.AddAuthorization();

Valores actuales en appsettings

En configuracion base y produccion, Entra esta declarado pero deshabilitado: 

"PulseCheck": {
  "Entra": {
    "Enabled": false,
    "TenantId": "",
    "TenantDomain": "",
    "ApiClientId": "",
    "WebClientId": ""

}
Para activar el flujo corporativo, Enabled debe ser true y TenantId + ApiClientId deben tener valores reales. En produccion tambien esta AllowLocalAdminLogin=false, por lo que si Entra queda deshabilitado no habra login administrativo local.

Configuracion frontend

El frontend no usa appsettings. Usa variables Vite expuestas en build/runtime: 

export const entraTenantId = import.meta.env.VITE_ENTRA_TENANT_ID?.trim() ?? ''
export const entraClientId = import.meta.env.VITE_ENTRA_CLIENT_ID?.trim() ?? ''
export const entraApiClientId = import.meta.env.VITE_ENTRA_API_CLIENT_ID?.trim() ?? ''
export const isEntraConfigured = Boolean(entraTenantId && entraClientId && entraApiClientId)

MSAL se crea solo cuando los tres valores existen. El clientId usado por el navegador es el registro de aplicacion web, mientras que el scope apunta al registro/API expuesta: 

const accessScopes = [`api://${entraApiClientId}/access_as_user`]

const msalInstance = isEntraConfigured
  ? new PublicClientApplication({
      auth: {
        clientId: entraClientId,
        authority: `https://login.microsoftonline.com/${entraTenantId}`,
        redirectUri: `${window.location.origin}/auth/callback`,
        navigateToLoginRequestUrl: false,
      },
      cache: {
        cacheLocation: 'sessionStorage',
      },
    })
  : null
El access token de Entra se mantiene en el flujo MSAL y se envia una vez a la API. Despues, el panel trabaja con el token interno de PulseCheck guardado bajo pulsecheck.admin.session.token.

Validacion del token Entra en la API

EntraAccessTokenValidator descarga metadata OpenID Connect por HTTPS desde el tenant configurado: 

var metadataAddress =
    $"https://login.microsoftonline.com/{_options.TenantId}/v2.0/.well-known/openid-configuration";

_configurationManager = new ConfigurationManager<OpenIdConnectConfiguration>(
    metadataAddress,
    new OpenIdConnectConfigurationRetriever(),
    new HttpDocumentRetriever { RequireHttps = true });

Para aceptar el token, la API valida emisor, audiencia, expiracion, firma y llaves de firma publicadas por Entra: 

var validationParameters = new TokenValidationParameters
{
    ValidateIssuer = true,
    ValidIssuers =
    [
        $"https://login.microsoftonline.com/{_options.TenantId}/v2.0",
        $"https://login.microsoftonline.com/{_options.TenantId}/v2.0/",
        $"https://sts.windows.net/{_options.TenantId}/"
    ],
    ValidateAudience = true,
    ValidAudiences =
    [
        _options.ApiClientId,
        $"api://{_options.ApiClientId}"
    ],
    ValidateLifetime = true,
    ValidateIssuerSigningKey = true,
    IssuerSigningKeys = configuration.SigningKeys,
    ClockSkew = TimeSpan.FromMinutes(2)
};

Ademas, el token debe traer el scope access_as_user. Si no esta, el login se rechaza: 

var scopes = principal.FindFirst("scp")?.Value
    ?.Split(' ', StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries)
    ?? [];

if (!scopes.Contains("access_as_user", StringComparer.OrdinalIgnoreCase))
{
    return null;
}

Del token se extraen los claims necesarios para autorizar internamente y enriquecer el usuario:

Dato Claims usados Uso interno
Email preferred_username, email, upn, unique_name Buscar el admin autorizado en AdminUsers.
Nombre name, preferred_username, email Actualizar DisplayName.
Object ID oid, sub Guardar EntraObjectId.
Tenant ID tid Guardar TenantId.

Endpoint de login corporativo

AuthController recibe el access token desde el frontend en POST /api/auth/entra. Primero verifica que la integracion este habilitada, luego valida el JWT y finalmente delega en AdminAuthService. 

[HttpPost("entra")]
public async Task<ActionResult<AdminSessionDto>> EntraLogin(
    [FromBody] AdminEntraLoginRequest request,
    CancellationToken cancellationToken)
{
    if (!entraAccessTokenValidator.IsEnabled)
    {
        return StatusCode(StatusCodes.Status503ServiceUnavailable,
            new { message = "El acceso corporativo no esta configurado." });
    }

    var validatedPrincipal =
        await entraAccessTokenValidator.ValidateAccessTokenAsync(request.AccessToken, cancellationToken);

    if (validatedPrincipal is null)
    {
        return Unauthorized(new { message = "No fue posible validar el token corporativo." });
    }

    var session = await adminAuthService.LoginWithEntraAsync(
        validatedPrincipal.Email,
        validatedPrincipal.DisplayName,
        validatedPrincipal.ObjectId,
        validatedPrincipal.TenantId,
        HttpContext.Connection.RemoteIpAddress?.ToString(),
        Request.Headers.UserAgent.ToString(),
        cancellationToken);

    return session is null ? Forbid() : Ok(session);
}

Autorizacion interna contra AdminUsers

El login Entra no concede acceso solo por pertenecer al tenant. Despues de validar el token, la aplicacion busca el correo normalizado en AdminUsers y exige que este activo y marcado como usuario Entra. 

var user = await unitOfWork.GetAdminUserByEmailAsync(normalizedEmail, cancellationToken);
if (user is null
    || !user.IsActive
    || !string.Equals(user.AuthenticationMode, "Entra", StringComparison.OrdinalIgnoreCase))
{
    return null;
}

El modelo de dominio guarda los campos que conectan el admin local con Entra: 

public sealed class AdminUser
{
    public string Email { get; set; } = string.Empty;
    public string DisplayName { get; set; } = string.Empty;
    public string? EntraObjectId { get; set; }
    public string? TenantId { get; set; }
    public string AuthenticationMode { get; set; } = "Local";
    public string PasswordHash { get; set; } = string.Empty;
    public bool IsActive { get; set; } = true;
}

La creacion de administradores desde AdminUsersController llama a CreateEntraAdminAsync. Ese servicio crea o actualiza usuarios con AuthenticationMode = "Entra", sin password local y activos.

Sesion interna AdminBearer

Cuando el usuario Entra esta autorizado, PulseCheck crea una sesion propia. El token devuelto al frontend es aleatorio; en base de datos se guarda solo el hash. 

var token = AdminSecurity.GenerateSessionToken();
var session = new AdminSession
{
    TokenHash = AdminSecurity.ComputeTokenHash(token),
    UserAgent = string.IsNullOrWhiteSpace(userAgent) ? null : userAgent.Trim(),
    IpAddress = string.IsNullOrWhiteSpace(ipAddress) ? null : ipAddress.Trim(),
    CreatedAtUtc = now,
    ExpiresAtUtc = now.Add(TimeSpan.FromHours(12))
};

Los endpoints administrativos usan [Authorize(AuthenticationSchemes = AdminTokenAuthenticationDefaults.Scheme)]. El handler AdminTokenAuthenticationHandler toma el bearer token, calcula su hash, busca la sesion, valida que no este revocada ni expirada y crea claims de usuario admin. 

var claims = new[]
{
    new Claim(ClaimTypes.NameIdentifier, session.AdminUser.Id.ToString()),
    new Claim(ClaimTypes.Email, session.AdminUser.Email),
    new Claim(ClaimTypes.Name, session.AdminUser.DisplayName),
    new Claim(ClaimTypes.Role, "Admin")
};

Variables que deben coincidir

Ambito Clave Valor esperado
API PulseCheck:Entra:Enabled true para habilitar POST /api/auth/entra.
API PulseCheck:Entra:TenantId Tenant ID de Microsoft Entra. Se usa para metadata, issuer y authority.
API PulseCheck:Entra:ApiClientId Client ID/app ID de la API expuesta en Entra. Debe coincidir con el audience del access token.
Web VITE_ENTRA_TENANT_ID Mismo tenant de la API.
Web VITE_ENTRA_CLIENT_ID Client ID de la aplicacion SPA/web registrada en Entra.
Web VITE_ENTRA_API_CLIENT_ID Mismo valor que PulseCheck:Entra:ApiClientId; arma el scope api://{id}/access_as_user.

Evidencia en pipelines: sin valores Entra hardcodeados

La configuracion de Entra ID no aparece embebida como tenant IDs, client IDs reales o secretos dentro de los YAML revisados. Los pipelines inyectan valores mediante variables de Azure DevOps, templates de variables y grupos de variables.

API pipeline

En PulseCheck-api/azure-pipelines-api.yml, el despliegue de App Service configura Entra ID mediante app settings, pero los valores vienen de variables $(...), no de literales reales. 

# Lineas relevantes: PulseCheck-api/azure-pipelines-api.yml
- group: PulseCheckBackDev

az webapp config appsettings set \
  --settings \
    PulseCheck__Entra__Enabled="true" \
    PulseCheck__Entra__TenantId="$(entraTenantId)" \
    PulseCheck__Entra__ApiClientId="$(entraApiClientId)" \
    PulseCheck__Entra__WebClientId="$(entraWebClientId)" \
    ConnectionStrings__PulseCheckDb="$(pulseCheckDbConnectionString)"
Evidencia Lectura
PulseCheck__Entra__TenantId="$(entraTenantId)" El tenant se toma de variable de pipeline, no de un GUID escrito en el YAML.
PulseCheck__Entra__ApiClientId="$(entraApiClientId)" El client ID de la API se inyecta como variable.
PulseCheck__Entra__WebClientId="$(entraWebClientId)" El client ID web tambien se inyecta como variable.
ConnectionStrings__PulseCheckDb="$(pulseCheckDbConnectionString)" La cadena de conexion no esta escrita en el YAML; se espera desde variable o grupo seguro.
- group: PulseCheckBackDev Para dev se usa un variable group de Azure DevOps, que permite administrar valores fuera del repositorio.

En PulseCheck-web/azure-pipelines-web.yml, el build de React recibe la configuracion Entra por variables de entorno Vite. Nuevamente, el YAML referencia variables y no contiene IDs reales.

Templates de variables

Los templates de produccion declaran las claves Entra, pero las dejan vacias. Esto demuestra que el repositorio no trae valores reales de tenant o client ID. 

# PulseCheck-api/pipelines/variables/prod.yml
entraTenantId: ''
entraTenantDomain: ''
entraApiClientId: ''
entraWebClientId: ''

# PulseCheck-web/pipelines/variables/prod.yml
entraTenantId: ''
entraClientId: ''
Resultado de verificacion local: se busco un patron de GUID en los YAML de API, Web y Agent, incluyendo templates de variables, y no se encontraron coincidencias. Eso cubre la forma esperada de tenant IDs y client IDs de Entra ID.
Observacion de configuracion: PulseCheck-web/azure-pipelines-web.yml usa $(entraApiClientId), pero PulseCheck-web/pipelines/variables/prod.yml no declara esa clave. Esto no es hardcode; es una variable pendiente de definir por template o variable group para que el build de produccion tenga el scope correcto.

Lectura tecnica final

  • La autenticacion corporativa esta implementada como federacion inicial con Entra ID y sesion propia posterior.
  • La API no confia solamente en el tenant: exige que el correo exista en AdminUsers con AuthenticationMode = "Entra".
  • El access token de Entra se valida manualmente con JwtSecurityTokenHandler y metadata OIDC, no mediante AddJwtBearer.
  • Los endpoints protegidos no usan directamente el JWT de Entra; usan AdminBearer, respaldado por AdminSessions.
  • El estado actual de archivos de configuracion deja Entra apagado, por lo que requiere inyeccion de valores reales en el despliegue.
  • Los pipelines revisados no tienen tenant IDs ni client IDs Entra hardcodeados; los valores se pasan como variables de Azure DevOps o quedan vacios en templates.
