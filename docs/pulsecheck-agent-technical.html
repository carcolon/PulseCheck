PulseCheck Agent · Documentacion tecnica

Este repositorio contiene el agente Windows que ejecuta PulseCheck en el endpoint del colaborador. El agente sincroniza campañas, muestra prompts interactivos, envía respuestas, reporta actividad de bloqueo/suspension y se actualiza automaticamente mediante feed de releases.

1. Objetivo del agente

Captura

Muestra preguntas en el escritorio del usuario y permite respuestas tipo escala, texto y si/no.

Operacion

Sincroniza campañas activas, reglas de entrega, estado de dispositivo y delivery logs con el backend.

Telemetria

Reporta eventos de lock, unlock, suspension y reanudacion con heuristica de inactividad previa.

2. Arquitectura actual del proceso

PulseCheck.Agent (WinExe)
├─ HostBuilder
│  ├─ Worker
│  ├─ CampaignNotificationListener
│  ├─ SessionActivityMonitorService
│  └─ AutoUpdateService
├─ WindowsPromptService
├─ PulseCheckApiClient
├─ LocalQueueStore
├─ LocalAgentStateStore
└─ TrayAgentApplicationContext

Modelo actual

  • El agente sigue siendo un solo proceso con UI de tray y servicios de fondo en la misma aplicacion.
  • No es todavia un Windows Service separado.
  • Usa VelopackApp.Build().Run() para compatibilidad con auto update.
  • Protege instancia unica con mutex de proceso.

3. Flujo operativo del agente

Inicio del agente
   |
   +--> carga appsettings.runtime.json
   +--> resuelve identidad del endpoint
   +--> arranca servicios de fondo
   +--> abre tray context

Loop operativo
   |
   +--> register / sync con API
   +--> recibe campañas activas
   +--> valida horario y reglas de entrega
   +--> muestra popup si corresponde
   +--> captura respuesta
   +--> envia respuesta y delivery log
   +--> escucha SignalR y polling
   +--> revisa feed de auto update

4. Componentes clave

Componente Funcion
Worker Loop principal de sincronizacion, orquestacion de campañas, prompts, cola local y envio al backend.
WindowsPromptService Popup WinForms para escala, texto y si/no. Si la campaña exige respuesta, fuerza visibilidad sobre apps normales de escritorio.
CampaignNotificationListener Escucha hub de notificaciones para despertar el loop sin depender solo de polling.
SessionActivityMonitorService Escucha SessionLock, SessionUnlock, Suspend y Resume; calcula inactividad y duracion.
AutoUpdateService Consume feed Velopack; si la instalacion no es Velopack managed, usa un fallback legacy con manifiesto JSON y ZIP.
TrayAgentApplicationContext Context menu, estado rapido, apertura de carpeta de datos y señal visible de version/canal.

5. Datos locales y estado

Archivos locales

  • appsettings.runtime.json: override empaquetado por pipeline.
  • agent-state.json: estado local persistido.
  • cola local de respuestas pendientes para tolerar fallos transitorios.
  • logs locales accesibles desde el tray.

Estado de runtime

  • AgentRuntimeState mantiene el resumen visible actual del proceso.
  • Estados visibles como En linea, Sincronizado, Esperando respuesta, En segundo plano.
  • Ese estado es de proceso actual; no reemplaza una consola de administracion central.

6. Auto update

Pipeline build
   |
   +--> dotnet publish
   +--> vpk pack
   +--> releases.win.json
   +--> *.nupkg
   +--> Setup.exe estable
   +--> agent-update.json
   |
Azure Blob Storage
   |
   +--> agente consulta feed
   +--> descarga nueva version
   +--> aplica update
   +--> reinicia

Consideraciones

  • El feed de update se aloja en Blob Storage con URL estable y accesible.
  • En dev el intervalo de chequeo se redujo a 5 minutos para pruebas.
  • El instalador estable para descarga publica es PulseCheck.Agent.Setup-dev.exe.
  • El instalador no se genera con dotnet-install; el pipeline usa UseDotNet@2 para preparar SDKs y vpk pack para crear el setup.
  • La validacion real del update se hace observando el cambio de version en el tray y los logs del agente.

7. Deteccion de inactividad, bloqueo y suspension

Evento Origen Dato reportado
SessionLock SystemEvents.SessionSwitch Segundos de inactividad al bloquear y clasificacion heuristica ManualLock o AutoLock.
SessionUnlock SystemEvents.SessionSwitch Duracion del bloqueo.
DeviceSuspended SystemEvents.PowerModeChanged Idle previo a suspension.
DeviceResumed SystemEvents.PowerModeChanged Duracion de suspension.
La deteccion de tapa cerrada no existe como evento de alto nivel en Windows para este modelo. La aproximacion implementada es detectar suspension y reanudacion, que cubre el caso normal de cierre de tapa en portatil.

8. Pipeline y artefactos

Build

El pipeline usa .NET 8 y .NET 9, publica el binario self-contained para Windows x64 y genera appsettings.runtime.json empaquetado.

Release

Velopack genera releases.win.json, paquetes .nupkg, instalador .exe, ZIP portable y manifiesto auxiliar.

Distribucion

Los artefactos se suben a un contenedor Blob de Azure. El pipeline del agente corre automaticamente en cambios de la rama dev.

El ejecutable principal es PulseCheck.Agent.exe: un ejecutable Windows x64 de escritorio generado por .NET como WinExe para net8.0-windows. El archivo de instalacion entregado al usuario es PulseCheck.Agent.Setup-*.exe, un instalador/bootstrapper Windows generado por Velopack.

9. Riesgos y limites vigentes

  • La arquitectura actual sigue siendo single-process con tray e interaccion de usuario en el mismo ejecutable.
  • No hay aun separacion formal en Windows Service + companion UI.
  • El prompt obligatorio puede reimponerse sobre apps normales, pero no puede sobreponerse al lock screen, UAC secure desktop ni algunos fullscreen exclusivos.
  • El control de cierre o desinstalacion solo puede endurecerse plenamente con una migracion a servicio Windows e instalacion per-machine administrada por TI.
